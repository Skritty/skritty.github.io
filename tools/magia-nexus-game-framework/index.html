Magia Nexus Game Framework

This page is under construction!

This is a comprehensive 2D and 3D game framework for rapid prototyping and implementation. It fully supports additions of new systems and mechanics for any type of game. While built in Unity, the framework itself is purely C# and could [relatively] easily be transferred to any other game engine that supports the language. I have used it in multiple projects and game jams in order to test and improve it over time, and more additions and improvements are planned.

While ECS frameworks are wonderful, I wrote my framework to be much more versatile for game development, allowing the developer to implement anything their heart desires without spaghetti code or hard limitations. Aside from entities and some data containers, no new instances of any of the mentioned components of the framework are ever created at runtime, so the framework itself will never have an impact on memory usage.

Magia Nexus is the game I am using the framework to create, but I intend on selling it on the Unity asset store after making a few more upgrades and default implementations/side features. Magia Nexus itself started as a Twitch chat autobattler game, but has evolved into a roguelite tactics game. It adds damage types, skills, actions, items, a map generator, and various mechanics such as formulaic spellcasting. The map generator is currently a work in progress and will become its own plugin. It utilizes the wavefunction collapse method of procedural generation and has its own editor tools to aid in setting up tile generation constraints.

The framework has a few key ideas:

  • Entities: Objects with a dynamic list of mechanics, akin to structs on an ECS entity. This framework is not quite ECS however. Entities in Unity are a component placed onto a GameObject.
  • Mechanics: Functionality that either needs to initialize stats and/or do something every game tick.
  • Stats: Modifiable variables bound to any object which can be accessed from anywhere provided you have the bound object. Stats can extend from different ‘solvers’ that determine how their modifiers calculate down into a singular fetchable variable. There are solvers that apply math, priorities, damage type calculations, merging lists, and more!
  • Modifiers: A variable container that modifies a stat. Solvers are modifiers too, so they have the potential to be nested. Modifiers can also be inherited stats of another object. There are different types of modifiers, such as duration modifiers, which only modify a stat for a number of game ticks before removing itself. 
  • Triggers: Classes with a statically bound object-action pairs. The action delegate always accepts one parameter. Triggers can be subscribed to via class or instance reference. A list of ‘tasks’ (or any compatible methods) are supplied alongside an optional ‘binding object’ and priority. From anywhere, a trigger can be invoked with a ‘binding object’ and parameter. Any matching or globally bound trigger subscriptions are invoked and passed the parameter.
  • Tasks: The intended recipient of a trigger invocation, and as such have a singular parameter, but may be run at any time. (Not to be confused with multithreading tasks). Tasks are a streamlined way to rapidly create small blocks of functionality that can be pieced together into something greater! Tasks are classes that return a boolean and happen in a set sequence. If one returns false, the sequence is aborted. This is used in ‘filter tasks’ to ensure that a sequence of tasks is valid when triggered. Tasks are primarily used alongside Odin Inspector (a wonderful Unity plugin) to quickly create sequences of functionality that can be anything from applying modifiers to an entity to firing projectiles to full behavior trees. Tasks are filtered by valid input parameter in the inspector, but the use of generically typed tasks allow their use anywhere (in cases where the input data in unimportant).

Entities

Mechanics

Mechanics are gameplay functionality that either needs to initialize as soon as the entity starts existing and/or do something every game tick. They are also the primary bridge between Unity objects in prefabs or the scene. Given a reference to the entity, mechanics can be accessed in case they have methods that need to be called.

public class NumericalSolver : Solver<float>, ICalculationComponent
{
    [field: SerializeField, FoldoutGroup("@GetType()"), HideIf("@this is IStat")]
    public CalculationStep Step { get; protected set; }

    public NumericalSolver() { }

    public NumericalSolver(CalculationStep method)
    {
        Step = method;
    }

    public NumericalSolver(float value, CalculationStep method)
    {
        Modifiers.Add(new DataContainer<float>(value));
        Step = method;
    }

    public override void Solve()
    {
        switch (Step)
        {
            case CalculationStep.Flat:
                {
                    _value = 0;
                    break;
                }
            case CalculationStep.Additive:
            case CalculationStep.Multiplicative:
                {
                    _value = 1;
                    break;
                }
        }
        
        foreach (IDataContainer<float> modifier in Modifiers)
        {
            (modifier as Solver<float>)?.Solve();

            switch (Step)
            {
                case CalculationStep.Flat:
                case CalculationStep.Additive:
                    {
                        _value += modifier.Value;
                        break;
                    }
                case CalculationStep.Multiplicative:
                    {
                        _value *= modifier.Value;
                        break;
                    }
            }
        }
    }

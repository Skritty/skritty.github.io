Magia Nexus Game Framework

Personal Project, 2024-2026
Project Page
GitHub

This is a comprehensive 2D and 3D game framework for rapid prototyping and implementation. It fully supports additions of new systems and mechanics for any type of game. While built in Unity, the framework itself is purely C# and could [relatively] easily be transferred to any other game engine that supports the language. I have used it in multiple projects and game jams in order to test and improve it over time, and more additions and improvements are planned.

The framework has a few key ideas:

  • Entities: Objects with a dynamic list of mechanics, akin to structs on an ECS entity. This framework is not quite ECS however. Entities in Unity are a component placed onto a GameObject.
  • Mechanics: Functionality that either needs to initialize stats and/or do something every game tick.
  • Stats: Modifiable variables bound to any object which can be accessed from anywhere provided you have the bound object. Stats can extend from different ‘solvers’ that determine how their modifiers calculate down into a singular fetchable variable. There are solvers that apply math, priorities, damage type calculations, merging lists, and more!
  • Modifiers: A variable container that modifies a stat. Solvers are modifiers too, so they have the potential to be nested. Modifiers can also be inherited stats of another object. There are different types of modifiers, such as duration modifiers, which only modify a stat for a number of game ticks before removing itself. 
  • Triggers: Classes with a statically bound object-action pairs. The action delegate always accepts one parameter. Triggers can be subscribed to via class or instance reference. A list of ‘tasks’ (or any compatible methods) are supplied alongside an optional ‘binding object’ and priority. From anywhere, a trigger can be invoked with a ‘binding object’ and parameter. Any matching or globally bound trigger subscriptions are invoked and passed the parameter.
  • Tasks: The intended recipient of a trigger invocation, and as such have a singular parameter, but may be run at any time. (Not to be confused with multithreading tasks). Tasks are a streamlined way to rapidly create small blocks of functionality that can be pieced together into something greater! Tasks are classes that return a boolean and happen in a set sequence. If one returns false, the sequence is aborted. This is used in ‘filter tasks’ to ensure that a sequence of tasks is valid when triggered. Tasks are primarily used alongside Odin Inspector (a wonderful Unity plugin) to quickly create sequences of functionality that can be anything from applying modifiers to an entity to firing projectiles to full behavior trees. Tasks are filtered by valid input parameter in the inspector, but the use of generically typed tasks allow their use anywhere (in cases where the input data in unimportant).

While ECS frameworks are wonderful, I wrote my framework to be much more versatile for game development, allowing the developer to implement anything their heart desires without spaghetti code or hard limitations. Aside from entities and some data containers, no new instances of any of the mentioned components of the framework are ever created at runtime, so the framework itself will never have an impact on memory usage.

Magia Nexus is the game I am using the framework to create, but I intend on selling it on the Unity asset store after making a few more upgrades and default implementations/side features. Magia Nexus itself started as a Twitch chat autobattler game, but has evolved into a roguelite tactics game. It adds damage types, skills, actions, items, a map generator, and various mechanics such as formulaic spellcasting. The map generator is currently a work in progress and will become its own plugin. It utilizes the wavefunction collapse method of procedural generation and has its own editor tools to aid in setting up tile generation constraints.

Simulation Modeling

UTD ATEC Capstone Project, Fall 2020
Project Page
GitHub
Download

A simulated volume using Position-Based Dynamics that can be interacted with in real time. It has a dynamically generated and updated mesh that can be exported to a .obj file. This was my senior capstone project at UTD. See the project page for in depth on my development process.

My implementation of Position-Based Dynamics (PBD) consists of 3 internal constraints, which each node in the simulation must attempt adhere to. They are compressive, stretch, and rotational constraints. Additionally there is an external static constraint that uses information from colliders to prevent the simulation from passing through them. The mesh is dynamically generated initially, then the vertices are updated in real-time as the nodes move around.

Reality Studio

Client Project at The Devhouse Agency, 2021
Project Page
GitHub

Reality Studio is a set of two applications and a Unity Editor tool developed solely by me. Its goal is to create an environment where interior design layouts can be quickly and easily created, changed, and viewed in a high fidelity AR experience by someone who is inexperienced with traditional 3d software.

The first application is called Content Creator, it is the 3d editor that allows the user to edit and manipulate an interior space. From there, a saved project can be uploaded to the second part of the pipeline. This is the Unity tool that uses AWS, Unity’s Lightbaking, and Unity Addressables to bundle the scene for mobile use. Once the project has been processed, it can be viewed within an AR environment on a phone or tablet.

Some of the more impressive systems I made found within the Content Creator app are:

  • Object and Surface Selection and Multi-Selection
  • Change History (Undo/Redo)
  • Mesh and Submesh Manipulation
  • Custom Project File Saving/Loading
  • Material and Preset Management

Additional information can be found on the project page. The linked Git repo will only contain individual systems out of context rather than the complete project. I would really recommend checking out the project page, there is too much to this project to put on this summary!

Portals

Personal Project, 2019

I have created multiple versions of portals/mirrors in Unity, improving with each iteration:
-(Old) A visual-only portal/mirror that renders to a texture on a plane.
-(Current) A visual and functional portal that uses a screen-space shader.
-(WIP) A visual and functional portal that combines the ideas of the previous two in order to make it seamless and extremely efficient, potentially allowing for many recursions.

Additional Info

Old: This version of the portal uses Unity’s physical cameras to position the POV from the other side of the portal so that its position matches the main camera’s, and so that its view frustum always exactly lines up with the surface of the portal. It renders this POV camera to a texture2d and uses it as the material’s texture on the portal plane. The positive of this method is that depending on the resolution you choose, it will have much less of an impact on FPS than the current method. The negative is that if you approach the portal plane close enough, you will easily be able to see the pixels of the texture.
Current: Unlike the old version, the POV camera of this one moves and rotates with the main camera, offset by whatever position and rotation the other side of the portal is in relation to the portal you are seeing. A culling matrix is used to render only what is in front of the linked portal. It is rendered to a texture2d and given to a shader that applies it to screen space. The positive is that regardless of how close you get to the portal plane, you will never see pixels, it is almost seamless. The negative is that, for each portal you need to render, you must render the entire screen resolution again, which is extremely expensive.
New WIP: This method uses a screen space shader, but limits what needs to be rendered. Cameras in Unity have a setting called “rect”, which determines where on the texture the rendering happens and what percentage of the texture it will take up. This is usually used to render mini-maps onto the screen. By calculating the smallest rectangle in screen space that a portal needs to fit into, I can limit the render to that rectangle and place it in the proper spot on the texture for it to be displayed properly using the shader. When recursively rendering portals, the amount of pixels needed to be rendered can be scaled down based on the size of the previous camera in the chain. Aside from a few edge cases, the number pixels that need to be rendered (including infinite recursion) should be at most around 2.5x the size of the screen. My hope is that this allows portals to be used in VR applications.

Wisps

UTD Virtual Environments Class, Spring 2019

A basic life simulation made in Unity that uses a Compute Shader to determine the behavior of each wisp.

Additional Info

Each tree contains one wisp and an internal storage of “light”. A wisp also has an internal storage of light. It takes 10% of the tree’s light when leaving the tree. The goal of each individual wisp is to increase the light of their tree. A wisp can only gain light by stealing it from a wisp that has more light than it. When it steals light, it takes 20% of the targeted wisp’s light. Wisps slightly favor closer candidates over farther away ones, even if the farther one has more light. Lastly, the more light a wisp carries, the slower it flies.


Because each wisp must take into account every other wisp (O(n^2)), a compute shader is used to speed up calculations. The only thing that needs to be determined is the target of each wisp based on the criteria list above, so it works well with the GPU.

Sprite Animation Controller

Personal Project, 2018

A state-based animator for 2d Unity that uses sprite sheets.

Animations are stored in Scriptable Objects. These contain each frame of the animation and other information about the animation such as animation time. The animator class contains functions used to play the animations. It does this using Coroutines.
